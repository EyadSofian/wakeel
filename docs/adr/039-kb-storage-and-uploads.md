# ADR-039 — Knowledge base storage and file uploads: ids, the upload flow, limits

Status: proposed (implemented as proposed in task 8.1; review with that PR) · Date: 2026-11-15

## Context

Architecture §2.3 lists the knowledge base tables and `files (id, bot_id?, purpose, key, mime, size, sha256)`. §8.1 says uploads come "from object store". Task 8.1 asks for upload with signed URLs, two-tenant tests, and size and MIME limits. The docs leave open:

1. Id prefixes for sources, ingestion jobs and files. `ENTITY_PREFIXES` has `kb`, `doc` and `chk` only.
2. How a file gets into the object store, and when the platform trusts that it arrived.
3. Which types and sizes are accepted.
4. The object key layout, so one tenant can never reach another's objects.

## Decision

1. **New entity prefixes:** `src` (kb_sources), `ijob` (kb_ingestion_jobs) and `file` (files), added to `ids.ts` and `common.ts`.
2. **Uploads go straight from the browser to the object store with a presigned `PUT`.** The api never proxies the bytes.
   - `POST /v1/workspaces/:ws/files { purpose, name, mime, size, botId? }` (`bot.update`) checks type and size, creates the `files` row with `status = 'pending'`, and returns `{ file, upload: { url, method: "PUT", headers, expiresAt } }`. The URL is valid for 15 minutes and is signed for that exact key, content type and length.
   - `POST /v1/workspaces/:ws/files/:fileId/complete` reads the object's metadata (HEAD). It refuses with `upload_incomplete` when the object is missing or its size or type differs. Otherwise it sets `status = 'ready'`, which is when a source may use the file.
   - `GET /v1/workspaces/:ws/files/:fileId/download` answers a presigned `GET` valid for 5 minutes (`bot.read`).
   - `sha256` is computed by the ingestion worker when it first reads the file (8.4), not by the client.
3. **Limits** (`FILE_LIMITS` in `packages/config`):
   - `kb_source` files: up to 50 MB, of type PDF, DOCX, PPTX, XLSX, HTML, Markdown, plain text, CSV, PNG and JPEG. These are the types the parser (8.2) reads.
   - Anything else is `validation_failed` on `mime` or `size`, with the allowed list or the limit in the message.
4. **Object keys** are `ws/<workspaceId>/files/<fileId>`. They are generated by the api, never taken from the client, and stored on the row. A presigned URL can only name that one key. Workers read objects by the key on a row they already read through `withWorkspace`, so RLS decides who reaches what.
5. **Object store access** goes through one `ObjectStore` interface in `packages/db` (S3 API via `@aws-sdk/client-s3`, Apache-2.0). Tests use an in-memory implementation.
   - `S3_PUBLIC_ENDPOINT` is the address presigned URLs use, which browsers must reach. It defaults to `S3_ENDPOINT`.

## Consequences

- A file can sit `pending` forever if the browser never finishes. The ingestion worker (8.4) adds a maintenance job that deletes pending files older than a day, with their objects.
- The object store's CORS must allow the Studio's origin for `PUT`. Task 8.1 does not set it yet: `create-bucket.sh` only creates the bucket. The Studio upload screen (8.8) adds it locally, and production deployment (15.5) must set it too.
