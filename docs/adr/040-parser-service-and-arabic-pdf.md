# ADR-040 — The parser service, and what to do when Arabic PDF text comes out broken

Status: proposed (blocks finishing task 8.2) · Date: 2026-11-15

## Context

Task 8.2 asks for `apps/parser` (Docling), an HTML path through Readability, an OCR tier through the vision model for low-text pages, and a parse-quality score. Its acceptance needs a born-digital Arabic PDF and a table across a page break to "produce expected headings and table cells".

What is built (branch `claude/phase-8-1-object-store-1ecac2`):

1. `apps/parser`: Python 3.12, FastAPI, Docling 2.150.1. `POST /v1/parse` takes the raw bytes with `Content-Type`, `X-File-Name` and `Authorization: Bearer $PARSER_TOKEN`. It answers per-page Markdown, character counts, headings and table cells. Limits: 50 MB, 500 pages, 180 s, one conversion at a time per process, and the declared type must match the file's magic bytes. Docling's own OCR is off. The parser has no network, so for pages under 40 characters it returns a PNG and **the worker** calls the vision model (`OcrPort`), capped per document.
2. `packages/retrieval/src/parse`: the client, HTML via Readability and Turndown, plain text and CSV without the parser, the OCR tier and the quality score. Unit tests cover them with Arabic fixtures.
3. Fixtures in `apps/parser/tests/fixtures`, generated by Chromium so Arabic shaping is real: a born-digital PDF, a 60-row price table over 3 pages, a scanned receipt (image only) and a DOCX.

**The finding.** DOCX, HTML and the scan behave as designed. Text-layer PDFs in Arabic do not, with any Docling backend:

| Backend | Result on the Arabic fixtures |
|---|---|
| docling-parse v2, v4 (default) | Lines with diacritics (tanween, shadda) break into fragments and lose words ("خلال ٤١ يوً"). Digit runs come out reversed (١٤ → ٤١, ١٠٠٠ → ٠٠٠١). Table cells and columns are in visual order ("1 رقم منتج", "متوفر غير", columns reversed). Lines without diacritics are correct. |
| pypdfium2 | Logical order is right, but the lam-alef ligature is decomposed backwards ("العمالء", "االسترجاع"), letters split by spaces ("م نتج"), and table structure is lost (one column). |

Indexed as-is, these pages would make Arabic search miss numbers, prices and negations ("غير متوفر"), which is the failure ADR-007 exists to prevent.

## Options

A. **Arabic text-layer pages go through the vision OCR tier.** The parser still returns Docling's structure, plus a page image for every page whose text is mostly Arabic. The worker OCRs those pages (capped per document, with the estimate shown before running, as the plan's risk note asks) and uses Docling's text only for non-Arabic pages. Most accurate, and predictable. Cost: one vision call per Arabic page. A 40-page Arabic PDF is 40 calls, charged to the workspace's key (or to the platform under BYOK rules).
B. **Repair the text in code.** Compare docling-parse and pdfium output per line, reverse visual-order runs, fix reversed digits, and re-join fragments. No model cost, but it is heuristics on heuristics. It will fix the fixtures and fail on the next PDF producer.
C. **Index as-is with a quality warning.** Cheapest, and wrong: Arabic PDFs are the main use case.
D. **A different PDF engine** (for example MuPDF, which is AGPL and so refused by our licence policy, or a commercial SDK). Not available under our rules without spending.

## Recommendation

**A**, with the cap configurable per workspace (default 50 pages per document) and the per-document estimate shown in the Studio before ingestion starts. The quality score stays as the second line of defence. B can come later as a cost reduction once the golden sets (8.7) can measure it.

## Consequences

- Ingesting an Arabic PDF costs model calls. Usage is recorded as `kind = "ocr"` with the KB's bot, and is billable as live usage only for live ingestion.
- Emulator and eval traffic is unaffected. Ingestion is not conversation traffic.
- The worker needs a vision-capable model configured; with none, Arabic PDF pages fall back to Docling's text with the `rtl_order` warning shown on the document.
- Python dependencies are not covered by `pnpm licences` yet. Docling (MIT), FastAPI (MIT), Uvicorn (BSD-3) and their tree (including PyTorch, BSD-3) need a Python licence check before 8.2 merges.
